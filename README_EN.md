# kimi-tide Tracking Study II: From "Picking a Model" to "Orchestration" — the Dispatch Layer, the Dispatch Guard, and the Making of a Quality OS (v1.0.0–v2.2.1)

> **Subject**: the open-source project [tafcear/kimi-tide](https://github.com/tafcear/kimi-tide) ("moon-tide") — a per-step model router and collaboration orchestrator for DeepSeek Harness (DSH). This is a longitudinal follow-up to the August 2026 study ("Architecture, Cost, and Feasibility", archived in this repo), covering **16 releases from v1.0.0 (2026-08-29) to v2.2.1 (2026-10-09)**.
>
> **Authors**: [tafcear](https://github.com/tafcear) (project author) × Kimi (AI research collaboration) ｜ Study date: 2026-10-09 ｜ Latest release: **v2.2.1 (2026-10-09)**

## Abstract

Forty days after v1.0.0, kimi-tide has changed shape three times. First, a **positioning pivot**: the front page moved wholesale from a "save money" axis to "orchestrate workflows and agents by each model's strengths" — cost savings demoted to a side effect. This is capability reality catching up with the narrative, not copywriting. Second, a **dispatch layer**: v2.0.0's "role = routing" (role table, sticky driver, dispatch ledger, a runtime skill card that puts the role table *into the model's view*) extended routing from "each step of the main session" to "each dispatched step"; v2.1.0 unified the information architecture with a five-tier decision chain and a single routing table (`routes`, config v7). Third — the focus of this study — a **quality operating system** took shape: six machine gates, a bilingual four-section release-notes gate, institutionalized post-release verification (asset sha256 vs API digest, character-for-character), and live acceptance runbooks promoted to a release prerequisite.

The period offers a textbook case: **the dispatch guard shipped in v2.2.0 never fired for its sole design target** — the predicate "is the caller a teammate" read the host's `{role: 'lead'}` return for root sessions as teammate identity, so anything the main session dispatched was never refused. Unit tests were green; the design doc said "main session ⇒ expect refusal"; that behavior never once occurred. Live acceptance for v2.2.1 caught and fixed it (issue #11), and two more "green tests, dead in production" wiring-layer defects were caught the same week (v2.0.0). All three sit on the seam between *the plugin's assumptions* and *the host's actual behavior* — which leads to this study's central claim: **in plugin architectures, the effective radius of unit tests ends at the host boundary; runtime observation and durable-source-of-truth checks (the child session's first `request/header`) are the only referees for wiring-layer semantics.**

## 1 The version line: sixteen releases in forty days

Test-count trajectory (release-gate records): 497 (v1.0.0) → 555 (1.1.0, review-flow claiming) → 582 (1.2.0, session-event decoupling; the new bilingual release-notes gate correctly blocked a non-compliant release on its first run) → 691 (1.3.0, usage/balance for all sources, semantic hit-confirmation gate, precise `@provider/model`) → 700 (1.3.1, host 0.1.7 migration) → 779 (1.4.0, **review loop closed**: auto/manual "send back and redo" with re-review and loop caps; desktop 0.2.0-rc.2 port) → 802 (1.4.1, effort-dropdown channel fix) → 925 (**2.0.0, dispatch layer**) → 1084 (**2.1.0, routing IA unification** + full locale-ization, 600 keys × 2 languages) → 1089/1129 (2.1.2 panel-scroll fix, 2.1.3 display-name secret guard) → 1158 (**2.2.0, dispatch guard** + repositioning + npm publishing) → 1170 (**2.2.1, guard predicate fix** + workflow scope + secrets gate). Six releases shipped on 2026-10-08 alone — each with the full gate suite green, evidence of pace *from* automation rather than at its expense.

## 2 The positioning pivot (v2.2.0)

The README rewrite (commit `3397d46`) moved the headline from cost to orchestration: "make 'which model for this step' something you can orchestrate" — three promises (each model does only the step it's best at; dispatched work follows roles too; you never have to remember to switch back), with review, savings, and observability demoted to "also included". The commit message is candid about why: the new positioning came out of the DSH discussion #9169, and the old README's front half (cost axis) and back half (role table / guard, orchestration axis) "weren't written in the same batch — the guard commit had just made the back half real while the header still sat on the old axis." The first study's observation that the project had "outgrown dual-model" is fully confirmed: the candidate pool is the host's entire Models page, GLM/qwen route in production, and "Kimi × DeepSeek" survives as the name and origin story.

## 3 The dispatch layer (v2.0.0)

Four mechanisms: a **role table** (`roles`: id + label + target model; teammate name = claim key; unclaimed teammates untouched); a **runtime skill card** (`kimi-tide-team`) that makes the role table visible to the model before it dispatches — extending routing discipline from user configuration into model behavior; a **sticky driver** (main session's default target pinned; rules and explicit `@` still win); and a **dispatch ledger** (basis `role`/`unclaimed`/`explicit`/`keep`, final effective model, 20 entries per parent session; an unavailable role target is *not* silently swapped — the panel says so verbatim).

Live acceptance (A1a–A8 all green; the one skipped item, role-reroute × image-latch, is explicitly "not executable due to host GUI limits — not counted as passed") caught two wiring-layer defects that all unit tests missed: ① optional-service probing via try/catch silently swallowed the host framework's *throw-on-undeclared-inject* behavior, silently disabling both the skill card and teammate lookup; ② the ledger was keyed by child-agent id, but children are destroyed on completion — the panel row was deleted the moment it was written. Both fixed with regression nails.

## 4 The dispatch guard: full lifecycle of a mechanism that never fired (v2.2.0 → v2.2.1)

**The gap was found, not guessed.** The role table's rerouting is *passive* — it only fires for `membership.role === 'teammate'`, so a bare `subagent`/`workflow` dispatch structurally cannot be rerouted. Worse, the plugin's own injected skill text used to say "dispatch to a subagent of the corresponding model" — a model following the instructions walked straight into the gap. v2.2.0's guard turns that dead end into a host-level refusal: monotonic final refusal on `ctx.tools.guard` (refuse-only, never auto-reroute), off by default, never throws, malformed args pass, and "prefer a miss over a false block" throughout.

**The defect.** v2.2.0 shipped with an honest IOU: "runtime refusal path not yet verified." The v2.2.1 acceptance run (2026-10-09) exercised it and found: main session dispatches a role-domain `subagent` → **allowed** (reproduced twice); the same words from a child agent → **refused**, reason returned verbatim. Registration, the guard channel, role matching, and the message text were all correct; the only broken piece was "is the caller a teammate": `tryMembership(executor) !== undefined` is always true because the host returns `{role: 'lead', name: 'lead'}` for a root session — the normal implicit-root-team return, verified by reading the desktop asar. **The behavior the doc specified had never once occurred.** The fix: `isTeammateMembership()` accepts only `role === 'teammate'` (same predicate source as the role table); a wiring-level regression nail (lead ⇒ still refused / teammate ⇒ pass / service absent ⇒ main-session semantics); and a self-inflicted mutation check — reverting the predicate turns the new test red, restoring it goes 29/29 green.

**The escape hatch that was a hole.** v2.2.0 left `workflow` out of scope as "the designed escape" (`agent()` takes explicit targets). A real incident on 10-08 broke that: three "independent review" subagents dispatched via `workflow` with `agent(prompt, { label, phase, schema })` — no `provider`/`model` — all ran on the default target while the dispatch description claimed "three different models". Rerouting logic had run and run correctly; **no step in the process was called "check the routing"**. v2.2.1 extends the guard: a `workflow` script whose `agent()` never names a target is refused, with both fixes and the explicit way out written in the reason. The predicate is deliberately a word-level heuristic — a script merely *mentioning* `model` counts as naming a target.

**Two-phase acceptance**, all archived: artifact-level predicate matrix against the built `lib/*.js` (39/39), config hot-remount, host-channel confirmation, and — after a host restart — four live judgements in the main session (domain-hit `subagent` refused; unnamed `workflow` refused; named `workflow` passes with the child's `request/header` matching the named target character-for-character; domain-free `subagent` passes). The one item not exercised live — "a teammate's own dispatch is not blocked" — was deliberately skipped because roster slots are non-reclaimable, covered instead by a wiring-level unit test plus the 2026-10-06 A2/A8 live evidence, and stated as such. The user then ruled: **the guard stays on permanently**.

## 5 Verification methodology, hardened

The guard case produced an explicit, written methodology (collaboration handbook §3.6, "verify after every dispatch — mandatory"): the **only** trustworthy predicate for "which model did the child actually run on" is the child session's first `request/header` event (the host's durable source of truth); session headers, `descriptor.agentModel`, and `list_agents` all drift after a reroute; dispatch descriptions are intent, not fact — *"I thought I passed it" is not evidence*. A script (`check-dispatch-routing.mjs`) operationalizes the check, and its usage caveats are documented too (a `--last N` window can straddle batches while the parent is still dispatching — a reported mismatch may be timing, not routing).

Rarer still: **the instruments themselves get repaired as defects**. One commit fixed three acceptance tools at once — one silently ignored unknown flags and reported PASS while reading the wrong profile (false pass), one hard-coded a previous version's feature list and was guaranteed to false-positive on every later release (false positive). Fixes: whitelisted flags with exit 2, version self-adaptation, per-version feature manifests. This extends the first study's "tests themselves must be debugged": **instruments must be acceptance-tested too**, or a green light is just instrument failure.

## 6 The quality OS: gates and release engineering

By v2.2.1 the repo runs **six machine gates**: ① four-way version consistency (CHANGELOG / package.json / both root READMEs / the package README's status line — the last added after two releases had silently drifted its body while bumping the status line, with two-directional negative controls); ② doc links (162 markdown files, zero broken); ③ bilingual README pair consistency; ④ terminology banned-words; ⑤ client i18n (AST-level scan of 18 browser-bundled sources, zh as sole source of truth with the en key set pinned at the type level); ⑥ the new **secrets gate** — assignment-style key fields and key literals in `cordis*.yml`, plus high-confidence shapes on the publish surface; hits print masked values only, and the predicate is *deliberately narrow* because the repo legitimately discusses key prefixes in many places: "**a gate that cries wolf gets turned off**". Release notes follow a bilingual four-section format gated locally and again in Actions; a pre-push coherence check cross-verifies that *the test count claimed in the release notes equals the measured count*; post-release verification compares downloaded asset sha256 against the API digest character-for-character.

Release engineering also surfaced an honest, still-open debt: since npm publishing began (v2.2.0), the npm and GitHub artifacts differ in line endings for 4 files (CRLF vs LF; root cause `core.autocrlf=true` with no `.gitattributes`; the other 81 files are byte-identical). The evidence log notes that the previous release's two-channel identity "was a coincidence of common origin", and schedules the fix — moving npm publish into CI with Trusted Publishing — for the next round. **As of v2.2.1 it remains open.**

## 7 A defect ethnography: the radius of unit tests ends at the host boundary

Eight fully documented "green tests, dead in production" defects across v1.3.0–v2.2.1 share one shape: the component's internal logic was entirely correct, and what broke was **the plugin's assumption about the host's or the outside world's behavior** — a reasoning-model judge burning its entire 64-token budget on thinking (silent fail-open, indistinguishable from "feature off"); a settings getter that always returns undefined plus a mismatched built-in key name (quota slots silently empty for GLM/Kimi); a `@provider` shorthand landing on the first pool candidate (403 on an unpurchased plan); a removed catalog channel returning an empty table that *overwrote* the real one; try/catch service probing vs throw-on-undeclared; ledger keyed by an ephemeral child id; `role: 'lead'` read as teammate; and `workflow` "explicitly targeted by design" — disproven by an incident. Static analysis, unit tests, and type checks missed all eight; live acceptance (six) and the user's own eyes (two) caught them. The project's institutional response is the practical form of this study's thesis: **no release ships until the live acceptance checklist is green on a real host — "unit tests green" ≠ "runs in the host"** — with session-log evidence anchored per item and "not executable" never counted as passed.

## 8 Open debts (as recorded, not counted as passed)

① role-reroute × image-latch live test (host GUI limitation); ② teammate-dispatch exemption (covered by unit test + prior live evidence); ③ the workflow predicate's miss direction (word-level heuristic); ④ the CRLF reproducibility gap (CI Trusted Publishing scheduled, not done); ⑤ the guard's silent degradation on registration failure is a booked debt — acceptable today (one less hint), unacceptable once role-scoped tool surfaces (Q11) hang *security* semantics on the same registration point; issues #9 (degradation must be visible or fail-closed) and #10 (guard capability boundary) are to be decided together; ⑥ the first study's largest gap still stands: **no offline replay evaluation** — "rule-driven vs score-driven" and "review loop vs solo strong model" remain backed by manual acceptance only, with the transfer-efficiency experiment deferred past v1.4.0.

## 9 Conclusions

**Product**: kimi-tide crossed from "per-step router" to "collaboration orchestration infrastructure" — role-based dispatch, a unified routing table, a five-tier decision chain, and an enforceable dispatch guard form a coherent orchestration semantics; the positioning pivot is the catch-up of narrative to capability. **Method**: all four conclusions of the first study survived tracking, and honesty proved itself as an engineering asset in the strongest way yet — **v2.2.0's honestly recorded "not yet verified" IOU directly led the v2.2.1 acceptance run to a blocking defect: honesty is not decoration, it is part of the defect-discovery mechanism.** **Engineering**: the effective radius of unit tests ends at the host boundary; runtime observation and durable-source checks are the only referees for wiring-layer semantics — and the three portable cornerstones are live acceptance as a release prerequisite, instruments treated as test subjects themselves, and the discipline that "I thought I passed it" is not evidence.

Watching next: issues #9/#10 (whether the governance engineering can carry real security boundaries), the Trusted Publishing fix, and — listed as the most important debt for the second study running — quantitative transfer-efficiency and offline-replay evaluation.
